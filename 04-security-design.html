1 安全架构总览

1.1 安全设计目标 — CIA 三要素

🔒 机密性 (Confidentiality)

确保用户密码、支付信息、手机号等敏感数据不被未授权访问。本项目通过 JWT 认证、HTTPS 传输加密、BCrypt 密码哈希、API 返回脱敏等手段实现。

✅ 完整性 (Integrity)

确保订单数据、库存数据在传输和存储过程中不被篡改。通过请求签名（HMAC-SHA256）、数据库乐观锁、Redis Lua 原子操作、接口幂等性设计保障。

⚡ 可用性 (Availability)

确保在高并发秒杀场景下系统稳定可用。通过 Nginx 限流、Redis + Lua 令牌桶限流、Sentinel 熔断降级、RabbitMQ 异步削峰等手段，保证系统在万级 QPS 下仍能正常服务。

2 身份认证与授权安全

2.1 JWT 安全设计

2.1.1 Token 结构

JWT Token 由 Header、Payload（Claims）、Signature 三部分组成：

// ===== Header =====
{
  "alg": "HS256",
  "typ": "JWT"
}

// ===== Payload (Claims) =====
{
  "userId": 100001,            // 用户ID
  "username": "buyer_zhang",    // 用户名
  "role": "BUYER",              // 角色: BUYER / SELLER / ADMIN
  "iat": 1706774400,            // 签发时间 (Issued At)
  "exp": 1706781600,            // 过期时间 (Expiration = iat + 2h)
  "tokenType": "access"         // token 类型标识
}

2.1.2 双 Token 方案

AccessToken
有效期 2 小时
每次请求携带
➔
过期前 5 分钟
前端检测 exp 字段
触发续期流程
➔
RefreshToken
有效期 7 天
仅用于换取新 AccessToken
➔
新 AccessToken
静默续期
用户无感知

安全要点：RefreshToken 仅存储于 HttpOnly Cookie（防 XSS 窃取），AccessToken 存储于内存变量（不用 localStorage）。RefreshToken 使用后旧 Token 立即失效（一次性轮换）。

2.1.3 签名算法

# application.yml
jwt:
  secret: ${JWT_SECRET}           # 256位随机密钥，存储于环境变量，绝不硬编码
  access-token-expiration: 7200    # 2小时 (秒)
  refresh-token-expiration: 604800 # 7天 (秒)
  algorithm: HS256

为什么密钥不能硬编码？密钥硬编码在代码中会随代码仓库泄露。攻击者获取密钥后可伪造任意用户的 JWT Token，直接绕过认证。应通过环境变量或配置中心（如 Nacos）注入。

2.1.4 Token 黑名单

// 用户登出时，将 Token 加入 Redis 黑名单
public void logout(String token) {
    Claims claims = jwtUtil.parseToken(token);
    long remainingMs = claims.getExpiration().getTime() - System.currentTimeMillis();

    if (remainingMs > 0) {
        // TTL = Token 剩余有效期，过期后自动清理
        String jti = claims.getId();
        redisTemplate.opsForValue().set(
            "token:blacklist:" + jti,
            "1",
            remainingMs,
            TimeUnit.MILLISECONDS
        );
    }
}

// 请求拦截时校验黑名单
public boolean isTokenBlacklisted(String token) {
    Claims claims = jwtUtil.parseToken(token);
    return Boolean.TRUE.equals(
        redisTemplate.hasKey("token:blacklist:" + claims.getId())
    );
}

2.2 Spring Security 配置

2.2.1 密码加密 — BCrypt

@Bean
public PasswordEncoder passwordEncoder() {
    // strength=10，每次加密约 100ms，有效防止暴力破解
    return new BCryptPasswordEncoder(10);
}

// 注册时加密
String encodedPassword = passwordEncoder.encode(rawPassword);

// 登录时校验
boolean matches = passwordEncoder.matches(rawPassword, storedHash);

为什么不用 MD5 / SHA256？MD5 和 SHA256 是快速哈希算法，专为数据校验设计，计算速度极快（每秒可计算数十亿次），极易被彩虹表和 GPU 暴力破解。BCrypt 是慢速哈希算法，内置随机盐（Salt），且 strength 参数可调（每增加 1 计算时间翻倍），使得暴力破解成本极高。

2.2.4 CSRF 策略

@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http
        .csrf(csrf -> csrf.disable())  // 禁用 CSRF
        .sessionManagement(s -> s.sessionCreationPolicy(
            SessionCreationPolicy.STATELESS  // 无状态会话
        ))
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/api/auth/**").permitAll()
            .anyRequest().authenticated()
        );
    return http.build();
}

为什么禁用 CSRF？CSRF 攻击依赖浏览器自动携带 Cookie 的机制。本系统使用 JWT（存于 Authorization Header），不依赖 Cookie 进行身份认证，浏览器不会自动附加 JWT，因此不存在 CSRF 风险。禁用 CSRF 可减少不必要的 Token 校验开销。

2.3 登录安全

2.3.1 连续登录失败锁定

// Redis 计数器实现：5 次失败后锁定 30 分钟
public LoginResult login(LoginRequest request) {
    String lockKey = "login:lock:" + request.getUsername();
    String failKey = "login:fail:" + request.getUsername();

    // 1. 检查是否已锁定
    if (Boolean.TRUE.equals(redisTemplate.hasKey(lockKey))) {
        return LoginResult.locked("账号已锁定，请30分钟后重试");
    }

    // 2. 验证密码
    if (!passwordEncoder.matches(request.getPassword(), user.getPassword())) {
        Long failCount = redisTemplate.opsForValue().increment(failKey);
        redisTemplate.expire(failKey, 30, TimeUnit.MINUTES);

        if (failCount >= 5) {
            redisTemplate.opsForValue().set(lockKey, "1", 30, TimeUnit.MINUTES);
        }
        return LoginResult.fail("用户名或密码错误");  // 统一提示，防枚举
    }

    // 3. 登录成功，清除失败计数
    redisTemplate.delete(failKey);
    return LoginResult.success(jwtService.generateTokens(user));
}

2.3.2 图形验证码触发

当同一用户连续登录失败 3 次后，登录接口要求额外提交滑块验证码（集成 hCaptcha），验证通过后才进行密码校验。

2.3.4 防枚举攻击

规则：所有登录失败场景统一返回 "用户名或密码错误"，不区分"用户不存在"和"密码错误"。避免攻击者通过不同的错误提示枚举有效用户名。

3 秒杀业务安全 核心重点

3.1 防黄牛 / 防刷策略 — 五层防御体系

秒杀场景面临的核心安全威胁是黄牛利用自动化脚本批量抢购。本系统设计了从前端到后端的五层递进式防御体系，每层独立生效、层层过滤：

1

第一层 · 前端限流（节流阀）

秒杀按钮点击后 1 秒内禁止重复提交（前端 throttle）。按钮置灰 + Loading 状态，防止用户疯狂点击。此为最轻量的第一道防线，仅防君子不防小人。

2

第二层 · 接口限流（令牌桶）

基于 Redis + Lua 令牌桶算法，每用户每秒仅允许 1 次秒杀请求。超出部分直接返回"请求过于频繁"。令牌桶允许小量突发但严格控制速率。

3

第三层 · IP 限流（滑动窗口）

单 IP 每分钟最多 30 次秒杀请求（Redis 滑动窗口算法）。有效防御单 IP 多账号并发刷单。超限后临时封禁该 IP 5 分钟。

4

第四层 · 验证码拦截

秒杀前需完成滑块验证码（集成 hCaptcha / Geetest）。验证码在秒杀活动开始前弹出，有效阻挡自动化脚本。验证码服务端校验 token 有效性及完成时间。

5

第五层 · 设备指纹

采集浏览器指纹（Canvas 指纹 + WebGL + 字体列表 + User-Agent + 屏幕分辨率），生成设备唯一标识。异常设备（同一指纹关联多个账号、请求频率异常）自动加入设备黑名单，后续请求直接拒绝。

令牌桶限流 — Redis + Lua 实现

-- rate_limiter.lua: 令牌桶限流脚本
-- KEYS[1] = 限流 key (如 rate:seckill:{userId})
-- ARGV[1] = 桶容量, ARGV[2] = 每秒填充速率, ARGV[3] = 当前时间戳(秒)

local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])

local bucket = redis.call('HMGET', key, 'tokens', 'last_time')
local tokens = tonumber(bucket[1]) or capacity
local last_time = tonumber(bucket[2]) or now

-- 补充令牌
local delta = math.max(0, now - last_time)
tokens = math.min(capacity, tokens + delta * rate)

if tokens >= 1 then
    tokens = tokens - 1
    redis.call('HMSET', key, 'tokens', tokens, 'last_time', now)
    redis.call('EXPIRE', key, 10)
    return 1  -- 允许
else
    redis.call('HMSET', key, 'tokens', tokens, 'last_time', now)
    redis.call('EXPIRE', key, 10)
    return 0  -- 拒绝
end

3.2 库存安全

3.2.1 Redis Lua 原子操作

库存预减和资格校验必须在同一个 Lua 脚本中完成，确保原子性，避免并发导致的超卖问题：

-- seckill_deduct.lua: 原子化库存预减
-- KEYS[1] = 库存 key (seckill:stock:{seckillId})
-- KEYS[2] = 已购集合 key (seckill:bought:{seckillId})
-- ARGV[1] = userId

-- 1. 检查是否已购买（防重复下单）
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return -2  -- 重复购买
end

-- 2. 检查库存
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil or stock <= 0 then
    return -1  -- 库存不足
end

-- 3. 扣减库存 + 记录已购
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return 1  -- 扣减成功

3.2.2 数据库乐观锁兜底

-- MySQL 乐观锁：WHERE stock > 0 防止超卖

SET stock = stock - 1
WHERE id = #{seckillId}
  AND stock > 0;

-- 检查 affected rows，若为 0 则说明库存已尽

3.2.4 库存对账

// 定时任务：每 10 分钟比对 Redis 与 MySQL 库存
@Scheduled(fixedRate = 600000)
public void reconcileStock() {
    List<SeckillGoods> goods = seckillMapper.selectAllActive();
    for (SeckillGoods g : goods) {
        Long redisStock = redisTemplate.opsForValue()
            .get("seckill:stock:" + g.getId());
        if (redisStock != null && !redisStock.equals(g.getStock())) {
            log.warn("库存不一致! seckillId={}, redis={}, mysql={}",
                g.getId(), redisStock, g.getStock());

        }
    }
}

3.3 订单安全

3.3.1 订单号生成 — 雪花算法 + 随机混淆

/**
 * 改进版雪花算法：在标准 Snowflake 基础上增加随机数混淆，
 * 防止订单号被枚举推算。
 * 结构：1位符号 + 41位时间戳 + 10位机器ID + 6位随机数 + 6位序列号
 */
public long nextOrderId() {
    long timestamp = System.currentTimeMillis() - EPOCH;
    long randomBits = ThreadLocalRandom.current().nextLong(64); // 6位随机
    long seq = sequence++ & 0x3F;  // 6位序列
    return (timestamp << 22) | (workerId << 12) | (randomBits << 6) | seq;
}

3.3.2 支付金额校验

核心原则：绝不信任前端传值。支付金额由服务端根据 orderId 查询数据库获取，前端传递的金额仅作为预校验比对，实际支付金额以服务端数据为准。

3.3.3 幂等性保障

// 支付接口幂等：同一 orderId 只处理一次
public PayResult pay(PayRequest request) {
    String orderId = request.getOrderId();
    String idempotentKey = "pay:idempotent:" + orderId;

    // Redis SETNX：仅第一个请求成功
    Boolean acquired = redisTemplate.opsForValue()
        .setIfAbsent(idempotentKey, "1", 30, TimeUnit.MINUTES);

    if (!Boolean.TRUE.equals(acquired)) {
        // 已处理过，返回之前的结果
        return PayResult.duplicate("请勿重复支付");
    }

    // 正常支付逻辑...
}

4 接口安全

4.1 防重放攻击

4.1.1 请求签名

/**
 * 请求签名生成：HMAC-SHA256(timestamp + nonce + body)
 * 客户端在请求头中携带：
 *   X-Request-Timestamp: 请求时间戳(秒)
 *   X-Request-Nonce:     随机字符串(16-32位)
 *   X-Request-Sign:      签名值
 */
public static String generateSign(String timestamp, String nonce, String body) {
    String data = timestamp + nonce + body;
    return HmacUtils.hmacSha256Hex(SECRET_KEY, data);
}

4.1.2 时间窗口校验

// 服务端校验：timestamp 与当前时间差 < 60 秒
long serverTime = System.currentTimeMillis() / 1000;
long requestTime = Long.parseLong(timestamp);

if (Math.abs(serverTime - requestTime) > 60) {
    throw new SecurityException("请求已过期，拒绝处理");
}

4.1.3 Nonce 去重

// Redis Set 存储已使用的 nonce，TTL 60秒

// 文件上传安全策略
private static final Set<String> ALLOWED_TYPES = Set.of(
    "image/jpeg", "image/png", "image/gif"
);
private static final long MAX_SIZE = 5 * 1024 * 1024; // 5MB

public String upload(MultipartFile file) {
    // 1. 校验 MIME 类型（白名单）
    if (!ALLOWED_TYPES.contains(file.getContentType())) {
        throw new SecurityException("不允许的文件类型");
    }
    // 2. 校验文件大小
    if (file.getSize() > MAX_SIZE) {
        throw new SecurityException("文件大小不能超过5MB");
    }
    // 3. UUID 重命名（防止路径穿越和文件名冲突）
    String ext = FilenameUtils.getExtension(file.getOriginalFilename());
    String newName = UUID.randomUUID().toString() + "." + ext;
    // 4. 存储到指定目录（非 Web 可访问目录）
    file.transferTo(new File(uploadDir, newName));
    return newName;
}

// 手机号脱敏工具
public static String maskPhone(String phone) {

}

# nginx.conf: 全局限流配置
# 定义限流区域：每秒 1000 请求（基于客户端 IP）

server {
    location /api/ {
        # burst=200: 允许突发 200 个请求排队
        # nodelay: 突发请求不延迟处理
        limit_req zone=global_limit burst=200 nodelay;
        limit_req_status 429;

        # 请求体大小限制
        client_max_body_size 5m;

        proxy_pass http://backend;
    }
}
