第一章缓存设计专题

缓存是高并发秒杀系统的第一道防线。合理的缓存设计可以将 99% 以上的读请求拦截在 Redis 层，极大降低数据库压力。本章从 Key 命名规范、缓存穿透/击穿/雪崩三大经典问题、以及缓存预热策略五个维度，详细阐述本项目的缓存架构设计。

1.1Redis Key 命名规范

统一的 Key 命名规范是缓存管理的基础。本项目采用 冒号分隔 + 业务前缀 + 实体标识 的三段式命名法，确保 Key 的可读性和可管理性。

命名原则

  • 冒号分隔：使用 : 作为层级分隔符，如 seckill:stock:1001，便于 Redis 可视化工具按层级展示
  • 业务前缀：第一个字段为业务域标识，如 seckill（秒杀）、rate（限流）、login（登录）、mq（消息队列）
  • 通配符管理：生产环境严禁使用 KEYS * 命令（O(N) 复杂度，阻塞主线程），统一使用 SCAN 游标迭代替代
  • TTL 必设：每个 Key 必须设置合理的过期时间，避免内存无限增长（秒杀库存等需要长期存在的 Key 由活动生命周期管理）

1.2缓存穿透（Cache Penetration）

问题定义

攻击者构造大量不存在的 Key（如 seckillId=999999），请求穿透缓存直达数据库。由于缓存中不存在该数据，每次请求都需要查询 MySQL，大量并发请求会直接打垮数据库。

方案一：空值缓存

查询数据库发现记录不存在时，在 Redis 中缓存一个空值标记（如 "NULL"），并设置较短的 TTL（2~5分钟）。后续对同一 Key 的请求直接命中缓存返回 null，无需访问数据库。

Java · SeckillGoodsService.java
@Service public class SeckillGoodsService { @Autowired private StringRedisTemplate redisTemplate; @Autowired private SeckillGoodsMapper goodsMapper; /** 查询秒杀商品详情（空值缓存方案）*/ public SeckillGoods getGoodsById(Long goodsId) { String key = "seckill:goods:" + goodsId; String cached = redisTemplate.opsForValue().get(key); // 缓存命中：区分空值标记和真实数据 if (cached != null) { return "NULL".equals(cached) ? null : JSON.parseObject(cached, SeckillGoods.class); } // 缓存未命中：查询数据库 SeckillGoods goods = goodsMapper.selectById(goodsId); if (goods == null) { // 数据库不存在 → 缓存空值标记，TTL=2min redisTemplate.opsForValue() .set(key, "NULL", 2, TimeUnit.MINUTES); return null; } // 数据库存在 → 缓存真实数据，TTL=30min + 随机偏移 long ttl = 30 * 60 + ThreadLocalRandom .current().nextInt(0, 600); redisTemplate.opsForValue() .set(key, JSON.toJSONString(goods), ttl, TimeUnit.SECONDS); return goods; } }

方案二：布隆过滤器（Bloom Filter）

布隆过滤器是一种空间效率极高的概率型数据结构，用于判断元素 "可能存在" 或 "一定不存在"。其核心原理是使用多个哈希函数将 Key 映射到位数组（Bit Array），写入时将所有哈希位置为 1，查询时检查所有哈希位是否都为 1。

布隆过滤器判断逻辑
  • 所有哈希位都为 1 → 元素 可能存在（有误判概率，需进一步查数据库确认）
  • 至少一个哈希位为 0 → 元素 一定不存在（100% 准确，直接拦截）
  • 误判率：与位数组大小和哈希函数个数相关。本项目配置 10万预期元素、1% 误判率，仅需约 114KB 内存
Java · BloomFilterInitializer.java
@Component public class BloomFilterInitializer implements ApplicationRunner { @Autowired private RedissonClient redisson; @Autowired private SeckillGoodsMapper goodsMapper; @Override public void run(ApplicationArguments args) { RBloomFilter<Long> bloomFilter = redisson.getBloomFilter("seckill:bloom:goods"); // 初始化：预计10万元素，误判率1% bloomFilter.tryInit(100000L, 0.01); // 加载所有有效秒杀商品ID List<Long> allIds = goodsMapper.selectList(null) .stream().map(SeckillGoods::getGoodsId) .collect(Collectors.toList()); allIds.forEach(bloomFilter::add); log.info("布隆过滤器初始化完成，加载{}个商品ID", allIds.size()); } } // === 查询时使用 === public SeckillGoods getGoodsWithBloom(Long goodsId) { RBloomFilter<Long> bf = redisson.getBloomFilter("seckill:bloom:goods"); if (!bf.contains(goodsId)) { return null; // 一定不存在，直接返回 } return getGoodsById(goodsId); // 可能存在，走缓存流程 }
布隆过滤器的局限性(1) 不支持删除：位数组是共享的，删除某个元素可能影响其他元素的判断。如需删除，需使用 Counting Bloom Filter 或定期重建。(2) 存在误判率：判断"存在"时有一定概率误判（1%），但判断"不存在"是 100% 准确的。(3) 不支持序列化迁移：Redis 中存储的位数组需通过 Redisson 客户端操作。

本项目策略

方案 A · 采用

商品详情查询 → 空值缓存

  • 秒杀商品数据量小（通常不超过 1000 个）
  • 实现简单，无额外依赖
  • 空值 Key 数量可控，内存占用极小
  • TTL=2min，恶意 Key 不会长期占用内存
方案 B · 采用

秒杀资格判断 → 布隆过滤器

  • 秒杀活动创建时预加载所有参与商品 ID
  • 高并发场景下第一层拦截无效请求
  • 1% 误判率可接受（误判后还有缓存层兜底）
  • 活动期间不需要删除操作

1.3缓存击穿（Cache Breakdown）

问题定义

某个热点 Key（如热门秒杀商品详情）在过期的瞬间，大量并发请求同时发现缓存 miss，导致所有请求同时穿透到数据库，形成瞬时 DB 压力洪峰。这与缓存穿透的区别在于：击穿是针对 存在的热点数据 的过期问题。

方案 A · 互斥锁

Mutex Lock 重建

原理：缓存 miss 时，通过 Redisson 分布式锁保证只有一个线程去查数据库并重建缓存，其他线程等待后重试。

  1. 缓存 miss → 尝试获取分布式锁
  2. 获取成功 → Double Check → 仍 miss → 查DB → 写缓存 → 释放锁
  3. 获取失败 → sleep 50ms → 重试（最多 3 次）
  • 优点：数据强一致，不会返回过期数据
  • 缺点：线程阻塞等待，有一定延迟
方案 B · 逻辑过期

Logical Expiration

原理：不设置 Redis TTL，在 Value 中嵌入逻辑过期时间字段。读取时检查是否过期，过期则异步重建，当前线程返回旧数据。

  1. 读取缓存值 → 解析逻辑过期时间
  2. 未过期 → 直接返回数据
  3. 已过期 → 尝试获取重建锁 → 异步线程重建缓存
  4. 当前线程立即返回旧数据
  • 优点：无阻塞、用户体验好
  • 缺点：短暂时间窗口内数据不一致

@Service public class CacheMutexStrategy { @Autowired private StringRedisTemplate redisTemplate; @Autowired private RedissonClient redisson; @Autowired private SeckillGoodsMapper goodsMapper; private static final int MAX_RETRY = 3; private static final long SLEEP_MS = 50L; public SeckillGoods getGoodsWithMutex(Long goodsId) { String key = "seckill:goods:" + goodsId; for (int retry = 0; retry < MAX_RETRY; retry++) { String cached = redisTemplate.opsForValue().get(key); // 1. 缓存命中 → 直接返回 if (cached != null) { return "NULL".equals(cached) ? null : JSON.parseObject(cached, SeckillGoods.class); } // 2. 缓存未命中 → 获取分布式锁 RLock lock = redisson.getLock("lock:goods:" + goodsId); boolean locked = lock.tryLock(0, 10, TimeUnit.SECONDS); if (locked) { try { // 3. Double Check：拿到锁后再查一次缓存 cached = redisTemplate.opsForValue().get(key); if (cached != null) { return "NULL".equals(cached) ? null : JSON.parseObject(cached, SeckillGoods.class); } // 4. 仍然 miss → 查数据库并重建缓存 SeckillGoods goods = goodsMapper.selectById(goodsId); if (goods == null) { redisTemplate.opsForValue() .set(key, "NULL", 2, TimeUnit.MINUTES); return null; } long ttl = 1800 + ThreadLocalRandom .current().nextInt(0, 600); redisTemplate.opsForValue() .set(key, JSON.toJSONString(goods), ttl, TimeUnit.SECONDS); return goods; } finally { lock.unlock(); } } // 5. 获取锁失败 → 等待后重试 Thread.sleep(SLEEP_MS); } return null; // 超过最大重试次数 } }

/** 缓存包装类：数据 + 逻辑过期时间 */ @Data public class CachedData<T> { private T data; private Long expireTime; // 逻辑过期时间戳(ms) } @Service public class LogicalExpirationStrategy { @Autowired private StringRedisTemplate redisTemplate; @Autowired private SeckillGoodsMapper goodsMapper; public SeckillGoods getGoodsWithLogicalExpire(Long goodsId) { String key = "seckill:goods:" + goodsId; String json = redisTemplate.opsForValue().get(key); if (json == null) return null; CachedData<SeckillGoods> cached = JSON.parseObject( json, new TypeReference<>(){}); // 未过期 → 直接返回 if (cached.getExpireTime() > System.currentTimeMillis()) { return cached.getData(); } // 已过期 → 尝试获取重建锁（SETNX 原子操作） Boolean locked = redisTemplate.opsForValue() .setIfAbsent("lock:rebuild:" + goodsId, "1", 10, TimeUnit.SECONDS); if (Boolean.TRUE.equals(locked)) { CompletableFuture.runAsync(() -> { try { rebuildCache(goodsId); } finally { redisTemplate.delete("lock:rebuild:" + goodsId); } }); } return cached.getData(); // 返回旧数据（短暂不一致可接受） } private void rebuildCache(Long goodsId) { SeckillGoods goods = goodsMapper.selectById(goodsId); if (goods == null) return; CachedData<SeckillGoods> newData = new CachedData<>(); newData.setData(goods); newData.setExpireTime(System.currentTimeMillis() + 30*60*1000); redisTemplate.opsForValue() .set("seckill:goods:" + goodsId, JSON.toJSONString(newData)); } }
本项目策略商品详情缓存使用 互斥锁方案（数据量不大，锁竞争小，数据一致性更重要）；秒杀库存不需要过期（活动维度管理，不存在 TTL 过期问题，从根源上避免了击穿）。

1.4缓存雪崩（Cache Avalanche）

问题定义

大量 Key 同时过期（如所有商品缓存同时到达 30min TTL），瞬间所有请求穿透到数据库，造成数据库连接池耗尽、响应超时甚至宕机。与缓存击穿的区别：击穿是单个热点 Key 过期，雪崩是 大面积 Key 集体过期。

策略一：TTL 随机偏移

在基础 TTL 上增加随机偏移量，打散过期时间点，避免大量 Key 同时失效。

Java · TTLRandomizer.java
/** * TTL 随机偏移工具 * 基础 TTL: 30min (1800s) * 随机偏移: 0 ~ 10min (0 ~ 600s) * 实际 TTL: 1800s ~ 2400s (30~40min) */ public static long randomTTL(long baseSeconds, int maxOffsetSeconds) { return baseSeconds + ThreadLocalRandom .current().nextLong(0, maxOffsetSeconds); } // 使用示例 long ttl = randomTTL(1800, 600); // 1800~2400 秒 redisTemplate.opsForValue() .set(key, json, ttl, TimeUnit.SECONDS);

策略二：多级缓存架构

构建从浏览器到数据库的多级缓存体系，每层缓存承担不同职责，逐级降低后端压力。

L1 · 浏览器缓存
Cache-Control: max-age=60 | 命中率 ~40% | 静态资源与商品列表
L2 · Nginx 本地缓存
proxy_cache + proxy_cache_valid 10s | 命中率 ~30% | 热点页面级缓存
L3 · Redis 分布式缓存
核心缓存层 | 命中率 ~95% | 商品详情、库存、用户状态
L4 · MySQL 持久化存储
最终数据源 | 仅处理缓存 miss 的写请求和少量读请求
缓存层级职责TTL 策略预期命中率适用数据
L1 浏览器拦截重复请求，减少网络传输max-age=60s~40%静态资源、商品列表页
L2 Nginx页面级缓存，减轻应用服务器压力10~30s~30%热点页面、活动页
L3 Redis核心数据缓存，拦截绝大部分读写30min+随机偏移~95%商品详情、库存、令牌
L4 MySQL持久化存储，最终一致性保障N/AN/A所有业务数据

策略三：热点数据永不过期 + 主动刷新

秒杀商品详情在活动期间不设置 TTL（永不过期），通过定时任务主动从数据库 reload 最新数据到 Redis，从根源避免过期问题。

@Component public class HotDataRefresher { @Autowired private StringRedisTemplate redisTemplate; @Autowired private SeckillActivityMapper activityMapper; @Autowired private SeckillGoodsMapper goodsMapper; /** 每5分钟刷新热点数据 */ @Scheduled(fixedRate = 300000) public void refreshHotGoods() { List<SeckillActivity> activeList = activityMapper.selectList( new LambdaQueryWrapper<SeckillActivity>() .in(SeckillActivity::getStatus, 1, 2)); for (SeckillActivity act : activeList) { List<SeckillGoods> goods = goodsMapper.selectList( new LambdaQueryWrapper<SeckillGoods>() .eq(SeckillGoods::getActivityId, act.getId())); for (SeckillGoods g : goods) { redisTemplate.opsForValue().set( "seckill:goods:" + g.getGoodsId(), JSON.toJSONString(g)); // 不设TTL } } log.info("热点数据刷新完成，活动数: {}", activeList.size()); } }

策略四：熔断降级兜底

当数据库 QPS 突增超过安全阈值时，触发熔断保护，避免数据库被打垮：

  • 一级熔断：数据库响应时间 > 500ms → 启用本地缓存（Caffeine），优先返回本地缓存数据
  • 二级熔断：数据库连接池使用率 > 90% → 直接返回预设默认数据或"系统繁忙"提示
  • 三级熔断：Sentinel 检测到异常比例 > 50% → 触发接口级熔断，所有请求直接走降级逻辑

1.5缓存预热策略

缓存预热是指在系统启动或新活动创建时，主动将热点数据从数据库加载到 Redis，避免冷启动时大量缓存 miss 导致数据库压力激增。

第二章Redis 与 MySQL 数据一致性方案

在"Redis 缓存预减 + MQ 异步下单"的架构下，Redis 中的库存数据与 MySQL 中的订单数据之间存在天然的一致性窗口。本章详细分析不一致场景并给出最终一致性的完整保障方案。

不一致场景枚举

场景 1：Redis 库存减了，MQ 消息发送失败

触发条件：DECR 执行成功，但网络异常导致消息未到达 Exchange。后果：Redis 库存被占用但永远不会生成订单，造成"幽灵扣减"。库存虚低，真实用户无法购买。

场景 2：MQ 消息消费失败（数据库写入异常）

触发条件：消费者收到消息但 MySQL INSERT 失败（连接超时、死锁、唯一约束冲突）。后果：Redis 库存已减但订单未创建，需回补库存。

场景 3：订单超时取消，Redis 库存回补失败

触发条件：订单 15 分钟未支付触发取消流程，MySQL 订单状态更新成功但 Redis INCR 失败。后果：MySQL 订单已取消但 Redis 库存未恢复。

场景 4：并发操作导致 Redis 库存与 MySQL 实际订单数不一致

触发条件：高并发下多个操作交叉执行（如回补和扣减同时进行）。后果：Redis 库存值与 MySQL 有效订单推算的库存值出现偏差。

(Integer) x.get(0).getOrDefault("count", 0) : 0; } private void restoreStockOnFail(SeckillOrderMessage msg) { try { redisTemplate.opsForValue() .increment("seckill:stock:" + msg.getSeckillId()); redisTemplate.opsForSet().remove( "seckill:bought:" + msg.getSeckillId(), msg.getUserId().toString()); } catch (Exception ex) { log.error("回补库存失败: {}", ex.getMessage()); } } }

4.2Redis 宕机降级方案

降级流程
  1. 检测机制：Redis 健康检查（每 5 秒 PING），连续 3 次失败标记为不可用
  2. 降级执行：秒杀接口切换到数据库乐观锁模式（UPDATE stock SET count=count-1 WHERE id=? AND count>0）
  3. 限流调整：降级后自动降低限流阈值（从 1QPS/用户 降到 0.5QPS/用户），保护数据库
  4. 恢复机制：Redis 恢复后自动切回缓存模式，触发缓存预热

@Component public class RedisHealthChecker { @Autowired private StringRedisTemplate redisTemplate; private volatile boolean available = true; private AtomicInteger failCount = new AtomicInteger(0); private static final int FAIL_THRESHOLD = 3; /** 每5秒检测 Redis 可用性 */ @Scheduled(fixedRate = 5000) public void check() { try { redisTemplate.opsForValue() .set("health:ping", "pong", 10, TimeUnit.SECONDS); failCount.set(0); if (!available) { available = true; log.info("Redis 恢复正常，切回缓存模式"); } } catch (Exception e) { int count = failCount.incrementAndGet(); if (count >= FAIL_THRESHOLD && available) { available = false; log.error("Redis 不可用(连续{}次失败)，触发降级!", count); } } } public boolean isAvailable() { return available; } }

4.5Sentinel 熔断配置

通过 Alibaba Sentinel 对核心秒杀接口进行流量控制和熔断降级保护。

核心熔断策略
  • 流量控制：秒杀接口 QPS > 100 时触发流控，超出部分直接拒绝
  • 熔断降级：异常比例 > 50% 触发熔断，熔断时长 10 秒
  • 半开探测：熔断 10 秒后进入半开状态，放行 1 个试探请求；成功则恢复，失败则继续熔断

熔断半开恢复机制

熔断状态（10秒）→ 半开状态（放行1个试探请求）→ 试探成功则 恢复 / 试探失败则继续 熔断。该机制确保系统能在故障恢复后自动切回正常模式，无需人工干预。
