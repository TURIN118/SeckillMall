一、设计简报 (Design Brief)

1.1 项目概述

本项目旨在设计并实现一个面向电商秒杀场景的高并发在线交易平台。平台模拟真实电商平台"双11""618"等大促活动中的限时秒杀场景——在指定时间点开放少量低价商品，瞬时涌入大量用户并发请求。系统的核心挑战在于：在高并发压力下保证库存不超卖、系统不崩溃、用户体验流畅，同时防范黄牛脚本恶意刷单。

项目定位为本科毕业设计，开发周期 4 个月（全职），采用单机部署 + JMeter 压测模拟高并发的方式，重点展示Redis 缓存策略、消息队列异步削峰、分布式锁、接口限流等高并发核心技术的设计与实现能力。

1.2 业务目标

核心业务目标

构建一个完整的电商秒杀平台，支持商品浏览、限时秒杀下单、在线支付（模拟）、订单管理等核心功能链路，系统在高并发场景下保持稳定可用。

技术展示目标

深度运用 Redis（缓存预热、库存原子扣减、分布式锁、用户资格标记）和消息队列（异步下单削峰、延迟消息取消超时订单），形成 4 个以上 Redis 应用场景 + 3 个以上 MQ 应用场景。

性能目标

秒杀接口单机 QPS 达到 5000+（优化后），秒杀下单响应时间 P99 < 200ms，库存扣减零超卖，系统可用性 > 99.5%（压测验证）。

学术目标

产出一份高质量毕业论文，以"问题驱动 → 技术方案 → 效果验证"为叙事主线，包含完整的技术选型对比、架构设计论证和 JMeter 压测报告。

1.4 设计策略与原则

性能优先原则

所有设计决策以"保障高并发下的系统可用性"为第一优先级。前端采用倒计时组件预渲染减少服务端请求，后端采用多级缓存 + 异步化架构降低数据库压力。

渐进式体验

秒杀流程设计为"浏览预热 → 倒计时等待 → 瞬时抢购 → 确认支付"四步渐进式体验，每一步都有明确的状态反馈和用户引导。

容错与降级

系统在每个环节都设计兜底方案：Redis 不可用时降级到数据库乐观锁、MQ 消息丢失时通过定时任务补偿、限流触发时返回友好排队提示。

极简 MVP 范围

聚焦核心秒杀链路（商品浏览 → 秒杀下单 → 支付 → 订单管理），省略物流、评价、推荐等非核心功能，深度优先于广度。

1.6 设计约束与边界

范围边界：本项目聚焦秒杀核心链路，不包含以下功能：真实支付对接（采用模拟支付）、物流追踪、商品评价、个性化推荐、多端适配（仅 Web PC 端）。支付环节模拟支付宝回调接口，重点展示支付状态流转设计。
部署约束：单机部署（1 台服务器 / 虚拟机），不做真正的分布式集群。通过 JMeter 多线程模拟高并发，论文中论证分布式架构设计的可扩展性。Redis 单节点、RabbitMQ 单节点、MySQL 单实例即可满足毕设演示需求。
时间约束：4 个月全职开发（2026 年 8 月 — 11 月），按"需求设计 2 周 → 基础开发 4 周 → 高并发改造 4 周 → 压测优化 3 周 → 论文答辩 3 周"节奏推进。

二、用户故事 (User Stories)

以下用户故事按角色维度拆解，每个故事包含 JTBD（Jobs To Be Done）、验收标准和设计触点，可直接指导后续的页面 Flow 设计与工程开发。

2.1 买家端用户故事

US-B01 注册与登录
作为一名新用户，我希望能够通过手机号 + 验证码或账号密码注册并登录，以便参与平台上的秒杀活动。

验收标准：

  • 支持手机号 + 密码注册，密码强度校验（8 位以上含大小写字母和数字）
  • 登录成功后返回 JWT Token，前端存储并自动附加到后续请求 Header
  • Token 有效期 24 小时，过期后自动跳转登录页
  • 登录失败时展示明确的错误提示（"密码错误" / "账号不存在"）
设计触点：注册页登录页全局导航栏
US-B02 浏览秒杀商品列表
作为一名买家，我希望能够在秒杀大厅浏览当前和即将开放的秒杀商品，以便提前了解商品信息并做好抢购准备。

验收标准：

  • 秒杀大厅展示"正在秒杀"和"即将开始"两个分区的商品列表
  • 每个商品卡片显示：商品图片、名称、原价、秒杀价、剩余库存百分比、倒计时
  • "即将开始"的商品显示精确的开始时间倒计时
  • 列表支持下拉加载更多，每次加载 10 条
设计触点：秒杀大厅页商品卡片组件倒计时组件
US-B03 查看商品详情
作为一名买家，我希望能够查看秒杀商品的详细信息，以便判断是否值得抢购。

验收标准：

  • 详情页展示：多图轮播、商品名称、详细描述、规格参数、原价 vs 秒杀价对比
  • 页面顶部固定显示秒杀状态条（倒计时 / "正在秒杀" / "已结束"）
  • 显示实时剩余库存（数据从 Redis 缓存读取，非数据库实时查询）
  • 详情页从 Redis 缓存加载，首次加载时间 < 500ms
设计触点：商品详情页秒杀状态条图片轮播组件
US-B04 参与秒杀抢购（核心）
作为一名买家，我希望能够在秒杀开始后第一时间抢购商品，以便以超低价格买到心仪的商品。

验收标准：

  • 倒计时结束前"立即抢购"按钮置灰不可点击，倒计时归零瞬间自动激活
  • 点击后按钮变为"抢购中…"loading 状态，禁止重复点击
  • 秒杀成功：弹窗提示"抢购成功，请在 15 分钟内完成支付"，自动跳转订单确认页
  • 秒杀失败（库存不足）：弹窗提示"手慢了，商品已被抢光"
  • 一人一单限制：同一用户对同一秒杀商品只能购买 1 件
  • 未登录用户点击"立即抢购"时跳转登录页
  • 接口限流：同一用户 1 秒内最多请求 1 次秒杀接口
设计触点：商品详情页-抢购按钮抢购结果弹窗倒计时组件
US-B05 确认订单与支付
作为一名成功抢到商品的买家，我希望能够确认订单信息并完成支付，以便最终获得这件秒杀商品。

验收标准：

  • 订单确认页显示：商品信息、收货地址（模拟）、应付金额、15 分钟支付倒计时
  • 点击"确认支付"调用模拟支付接口，支付成功后跳转"支付成功"页
  • 15 分钟未支付 → 系统自动取消订单 + 回补 Redis 库存 + 推送取消通知
  • 用户可主动点击"取消订单"，取消后库存立即回补
设计触点：订单确认页支付倒计时支付成功页订单取消弹窗
US-B06 查看与管理订单
作为一名买家，我希望能够查看我的所有订单并管理订单状态，以便随时了解购买情况。

验收标准：

  • 订单列表页支持按状态筛选：全部 / 待支付 / 已支付 / 已取消 / 已完成
  • 每个订单卡片显示：商品图片缩略图、名称、秒杀价、订单状态标签、操作按钮
  • 待支付订单显示剩余支付时间倒计时，超时自动变为"已取消"
  • 支持分页加载，每页 10 条
设计触点：我的订单页订单卡片组件状态筛选标签页

2.2 运营端用户故事

US-S01 创建秒杀活动
作为一名运营人员，我希望能够快速创建秒杀活动并配置商品信息，以便高效组织促销活动。

验收标准：

  • 创建秒杀活动表单：选择商品 → 设置秒杀价格 → 设置秒杀库存 → 设置开始/结束时间
  • 秒杀价不得高于商品原价，库存不得超过商品总库存
  • 创建成功后活动进入"待开始"状态，到达指定时间自动激活
  • 活动创建后自动将商品信息预热到 Redis 缓存
设计触点：秒杀活动管理页创建活动表单商品选择器
US-S02 查看活动数据概览
作为一名运营人员，我希望能够实时查看秒杀活动的关键数据指标，以便评估活动效果并做出调整。

验收标准：

  • 活动详情页展示：参与人数、下单总量、成交金额、库存消耗进度条
  • 数据以可视化图表呈现（折线图：下单趋势，饼图：成交/未成交占比）
  • 支持导出活动数据为 Excel 文件
设计触点：活动数据看板统计图表组件数据导出按钮

2.3 管理员端用户故事

US-A01 商品管理
作为一名管理员，我希望能够对平台商品进行完整的增删改查操作，以便维护商品数据的准确性。

验收标准：

  • 商品列表页支持搜索、分类筛选、分页，每页 20 条
  • 新增商品：上传图片、填写名称/描述/价格/库存/分类
  • 编辑商品信息后自动清除 Redis 中的缓存数据，保证数据一致性
  • 商品下架后相关秒杀活动自动失效
设计触点：商品管理列表页商品编辑表单图片上传组件
US-A02 用户管理与权限控制
作为一名管理员，我希望能够管理平台用户账号和角色权限，以便保障系统安全。

验收标准：

  • 用户列表支持搜索、角色筛选、状态筛选（启用/禁用）
  • 支持禁用/启用用户账号，禁用后该用户无法登录
  • 支持修改用户角色（普通用户 / 运营人员 / 管理员）
  • 角色权限变更后立即生效（下次请求时校验新权限）
设计触点：用户管理页角色分配弹窗操作日志记录
US-A03 系统监控仪表盘
作为一名管理员，我希望能够通过仪表盘直观地监控系统运行状态，以便及时发现和处理异常。

验收标准：

  • 仪表盘展示：今日订单数、今日成交额、活跃用户数、Redis 缓存命中率
  • 系统健康指标：CPU/内存使用率、Redis 连接数、RabbitMQ 队列积压量
  • 关键指标异常时显示红色预警标识
  • 数据每 30 秒自动刷新
设计触点：系统仪表盘指标卡片组件预警提示组件

四、用户旅程 (User Journey)

4.1 用户全生命周期旅程

以下旅程地图以买家"小李"为视角，从发现平台到完成秒杀的完整体验链路。每个阶段标注用户目标、触点、情绪曲线、痛点和设计机会点。

1
发现 — Awareness
用户目标
从朋友分享 / 社交媒体得知平台有限时秒杀活动
触点
社交媒体链接、搜索引擎、朋友推荐
痛点
不确定平台是否可信，担心是虚假促销
机会点
首页突出展示"正品保障"和"已成交订单数"增强信任
2
探索 — Consideration
用户目标
浏览秒杀大厅，查看有哪些值得抢购的商品
触点
首页秒杀大厅、商品卡片列表、分类导航
痛点
商品太多不知道哪个划算，缺少"折扣力度"排序
机会点
商品卡片显示折扣百分比 + "热门" / "即将售罄"标签引导决策
3
注册 — Onboarding
用户目标
注册账号以便参与秒杀
触点
注册页、登录页、全局导航栏
痛点
注册流程繁琐会直接流失，验证码等待时间长
机会点
支持手机号快速注册，注册完成后自动登录并跳转到之前浏览的商品页
4
等待 — Activation
用户目标
进入商品详情页，等待秒杀开始
触点
商品详情页、倒计时组件、秒杀状态条
痛点
不知道精确的开抢时间、担心手速不够快
机会点
精确到毫秒的倒计时 + "开抢前 10 秒"振动提醒（移动端） + 页面保持常亮
5
抢购 — Engagement（核心时刻）
用户目标
倒计时归零瞬间抢购商品
触点
"立即抢购"按钮、抢购结果弹窗
痛点
点击后长时间无响应、不知是否成功、重复点击

点击后 200ms 内展示 loading → 1-3 秒内返回结果；按钮立即置灰防重复点击
6
支付 — Retention
用户目标
在 15 分钟内完成支付确认
触点
订单确认页、支付倒计时、支付结果页
痛点
支付流程不清晰、忘记支付导致订单取消
机会点
醒目的支付倒计时 + 即将到期时弹窗提醒 + 支付成功页展示"恭喜"动效

4.2 秒杀核心旅程（放大视角）

以下是"抢购 — 支付"这一段最关键的 30 秒旅程的时间线拆解，精确到每个用户动作和系统响应：

时间线用户动作系统响应用户情绪设计要点
T-60s 进入商品详情页 从 Redis 加载商品缓存数据 期待 页面首屏加载 < 500ms，显示实时库存
T-30s 盯着倒计时 倒计时组件前端本地计时（不发请求） 紧张 倒计时数字放大加粗，最后 10 秒红色闪烁
T-0s 疯狂点击"立即抢购" 按钮激活，接收第一次请求，后续请求被限流 焦急 按钮变大变醒目，首次点击后立即变 loading 态
T+0.2s 看到按钮变为"抢购中…" 后端执行 Redis Lua 脚本预减库存 屏息 Loading 动画给用户"系统在处理"的确定感
T+1-3s 等待结果 库存预减成功 → 发送 MQ 消息 → 异步创建订单 期待 如果超过 3 秒显示"正在排队处理"提示
T+2-5s 看到结果弹窗 返回秒杀结果（成功/失败） 狂喜/失落 成功：绿色弹窗 + "去支付"按钮；失败：灰色提示 + "查看其他"
T+5-30s 进入订单确认页 展示订单信息和 15 分钟支付倒计时 紧迫感 支付倒计时醒目展示，强调"逾期自动取消"
T+30-60s 确认并点击"支付" 调用模拟支付接口 → 更新订单状态 满足 支付成功页展示"恭喜获得" + 订单摘要

D-3：Token 管理与权限路由 全局机制（无独立页面）
请求拦截（Axios Request Interceptor）
  • 每次请求前从 Pinia userStore 读取 Token
  • 自动在请求 Header 中附加 Authorization: Bearer {token}
  • Token 为空时不附加 Header（公开接口正常调用）
响应拦截（Axios Response Interceptor）
  • 401 Unauthorized：清除 Token（Pinia + localStorage）→ 跳转 /login?redirect={当前路径} → Toast "登录已过期，请重新登录"
  • 403 Forbidden：跳转 403 无权限页面 → 显示"您没有权限访问该页面" + "返回首页"按钮
  • 500 Server Error：Toast "服务器异常，请稍后重试"（不跳转）
  • 网络超时（timeout: 10s）：Toast "请求超时，请检查网络后重试"
路由守卫（Vue Router beforeEach）
  • 检查目标路由 meta.requiresAuth：若为 true 且无 Token → 重定向 /login?redirect={目标路径}
  • 检查目标路由 meta.roles：若当前用户角色不在允许列表中 → 重定向 403 页面
  • 后台路由 /admin/*：登录后根据用户角色动态注入路由（普通用户不可访问后台）
  • 已登录用户访问 /login 或 /register → 自动重定向到首页
Token 过期管理
  • Token 有效期：默认 24 小时（勾选"记住我"为 7 天）
  • 过期前 5 分钟提醒：前端定时器每 60 秒检查 Token 过期时间（从 JWT payload 的 exp 字段解析），距过期 < 5 分钟时弹窗"登录即将过期，请重新登录" + "重新登录"按钮
  • 点击"重新登录"：跳转登录页（携带 redirect 参数），登录成功后回到当前页面
  • 忽略提醒：Token 过期后下一次请求自动触发 401 拦截流程

7.2 前端技术架构详解

项目结构

采用 Vue 3 + Vite + TypeScript 技术栈，按功能模块组织：src/views/（页面组件）、src/components/（通用组件）、src/stores/（Pinia 状态）、src/api/（接口封装）、src/router/（路由配置）、src/utils/（工具函数）。

状态管理策略

Pinia 管理三类全局状态：userStore（登录态、Token、角色）、cartStore（购物车/秒杀商品暂存）、seckillStore（倒计时状态、秒杀结果轮询状态）。状态持久化到 localStorage（Token）。

请求层设计

Axios 封装统一拦截器：请求拦截自动附加 Authorization: Bearer {token}；响应拦截处理 401（跳转登录）、403（无权限提示）、500（错误 Toast）。所有 API 按模块拆分为独立文件。

路由权限控制

Vue Router 全局守卫：beforeEach 中校验路由 meta.requiresAuth 和 meta.roles，未登录跳转 /login?redirect=xxx，角色不匹配跳转 403 页面。后台路由动态添加（登录后根据角色注入）。

7.3 后端技术架构详解

7.3.1 Redis 四大应用场景

场景数据结构实现方式解决的问题
商品详情缓存 String（JSON 序列化） Key: seckill:goods:{id}，TTL: 30min，活动创建时预热 避免秒杀高峰期大量请求打到 MySQL
库存预减（核心） String + Lua 脚本 Key: seckill:stock:{seckillId}，Lua 脚本原子执行：判断库存 > 0 → DECR → 判断用户是否已购买 → SADD 用户集合 原子性保障库存不超卖 + 一人一单校验

Lua 脚本原子操作示例（库存预减）：

7.3.2 RabbitMQ 三大应用场景

场景队列类型实现方式解决的问题
异步下单削峰（核心） 普通队列 + Direct Exchange 秒杀请求通过 Redis 预减后发送 MQ 消息 → 消费者异步创建订单写入 MySQL。Exchange: seckill.exchange，Queue: seckill.order.queue 将瞬时高并发请求从同步转为异步，MySQL 只承受消费者匀速消费的写入压力
超时订单自动取消 延迟队列（RabbitMQ TTL + 死信交换机） 订单创建后发送 TTL = 15 分钟的消息到延迟队列 → 消息过期后路由到死信队列 → 消费者检查订单是否已支付 → 未支付则取消 + 回补 Redis 库存 替代定时任务轮询方案，精确到秒级的超时取消，不浪费数据库资源
秒杀结果通知 Fanout Exchange 订单创建成功后发送广播消息 → 消费者更新 Redis 中的秒杀结果标记 → 前端轮询结果接口时直接从 Redis 获取 解耦秒杀结果的处理，支持后续扩展（如短信通知、推送等）

7.4 关键技术选型对比

消息队列选型：RabbitMQ vs RocketMQ vs Kafka
RabbitMQ（选用）

延迟：微秒级，适合业务场景
Spring Boot 集成极为成熟（spring-boot-starter-amqp）
内置延迟队列方案（TTL + DLX）
管理界面友好，学习曲线低
单机吞吐量万级，毕设场景完全够用
社区文档丰富，问题排查方便

RocketMQ / Kafka（未选）

RocketMQ：单机部署配置复杂，Spring Boot 集成不如 RabbitMQ 成熟，更适合阿里系大规模场景

Kafka：设计目标是高吞吐日志处理（百万级 TPS），延迟较高（毫秒级），对于订单类业务消息偏重，且延迟消息支持不如 RabbitMQ 原生

ORM 框架选型：MyBatis-Plus vs Spring Data JPA
MyBatis-Plus（选用）

SQL 可控，方便在论文中展示复杂 SQL 优化
内置通用 CRUD + 分页插件 + 条件构造器
国内 Java 开发主流选择，校招面试认可度高
支持自定义 SQL 实现乐观锁（UPDATE stock SET count=count-1 WHERE id=? AND count>0）

Spring Data JPA（未选）

Hibernate 自动生成的 SQL 不够透明，不利于论文中展示 SQL 优化过程
复杂查询需要写 JPQL 或 Criteria API，学习成本不低但灵活性不如 MyBatis

UI 组件库选型：Element Plus vs Ant Design Vue vs Naive UI
Element Plus（选用）

Vue 3 生态最成熟的企业级组件库
组件丰富（60+），后台管理场景覆盖最全
中文文档和社区资源最丰富
国内使用率最高，毕设答辩导师熟悉度高

Ant Design Vue / Naive UI（未选）

Ant Design Vue：设计规范偏重，组件风格更适合中大型企业应用，对毕设而言偏重

Naive UI：Vue 3 原生，TypeScript 友好，但组件数量较少、社区资源不如 Element Plus 丰富
